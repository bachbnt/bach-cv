bach-cv: data design

The Firestore model behind the site: what is stored, how it reaches the page, how remote config works, who may read what, and how it moves to SQL.

1. Principles

The data lives in Firestore today and is shaped so that it can move to SQL without changing the app. The contract is src/lib/content/schema.ts (Zod); the app only talks to the data through src/lib/content/repository.ts.

#RuleWhy it helps a SQL move
1One collection is one table. A document id is a slug and the primary key.id TEXT PRIMARY KEY
2A reference to another document is always its id, never a path.becomes a foreign key
3One type per field. No unions, no "1" next to 1.one type per column
4No missing fields: null for numbers, dates and ranks; empty text for strings. Every field is written.NOT NULL DEFAULT ''
5An array of ids is a many-to-many table with a position. An array of strings or objects is a child table with a position. Nothing nests deeper.experience_skill, experience_bullet
6Dates are strings: YYYY-MM for periods, YYYY-MM-DD for days. No Timestamp in content.sorts correctly as text
7Field names are lowerCamelCase and avoid SQL words: sort, category, startMonth, menuGroup.no quoting
8Translations are an overlay on the same field names, not a second copy of the document.an l10n table

Simplifications against the first version: no per-field visibility flags (an empty field is simply not shown), no pages or i18n collections (interface copy lives in code), and no manual order for data that has dates.

3. How the data reaches the page

Only site/shell is embedded when the site is built. Everything else is read in the browser with firebase/firestore/lite (one-shot reads, no listeners) and cached by TanStack Query.

5. Remote config

Edit a document in the Firebase console; the site follows without a build.

You setThe site does
visible: false on any content documentthe item disappears; the rules stop returning it, so it is not downloadable either
highlight: 1, 2, 3 (projects, payments, skills)featured first, in rank order
site/live.pages.payment = "soon"the menu shows Payment with a Soon badge; the URL shows Coming soon
site/live.pages.payment = "hidden"the menu entry goes; the URL shows the 404 screen
site/live.features.chat = falsethe floating button, the Ask BB Bot buttons and the chat card disappear
site/live.features.cvDownload = falsethe Download CV buttons disappear
site/live.features.contactForm = falsethe form is replaced by a short note
site/live.features.connectMenu = falsethe Connect button disappears
site/live.maintenance.enabled = truethe whole site is replaced by a maintenance screen with your message (and Vietnamese in l10n.vi.message)
l10n.vi.summary etc.the Vietnamese text for that field
A hidden page is a UI switch: its content is still in the static files. Sensitive data is protected by visible and the rules, and payments are never embedded.

All switches fail open: if site/live cannot be read, every page and feature is on and maintenance is off.

6. Languages

English is the base text in every document. A document may carry an overlay for Vietnamese:

experience/fpt-software
  role: "Team Lead"
  summary: "Own delivery of the FPT-scope functions, ..."
  l10n:
    vi:
      role: "Trưởng nhóm (Team Lead)"
      summary: "Chịu trách nhiệm giao các chức năng thuộc phạm vi FPT, ..."

localize(doc, lang) lays the overlay over the base; a field with no translation keeps the English text. The schema lists which fields are translatable per collection (a key outside the list is dropped), so a typo cannot silently do nothing. Interface copy is separate: it lives in src/content/copy/*.ts as defineCopy(en, vi).

7. Access rules

firestore.rules, deployed to the project. The old site's collections (config, user, message) are closed to browsers; their data is kept.

PathBrowser canCondition
site/shell|live|profile|settingsreadalways; never write
skills experience education projects certificates services payments contactsget, listresource.data.visible == true: the query must include where('visible', '==', true) or the whole query is rejected
messagescreate onlyonly name, email, topic, message, locale, createdAt; name 1-100, email format and ≤ 254, message 1-1000, topic ≤ 40, locale en|vi, createdAt == request.time
everything elsenothingdenied

Verified against the real project as an anonymous visitor: visible queries succeed; a query that could return hidden payments is rejected; a hidden payment cannot be read by id; writes to content and reads of messages are denied; invalid messages are rejected; the old v1 collections are denied. The browser queries have no orderBy (it would need a composite index); lists are sorted in memory.

8. Moving to SQL

The tables are in docs/schema.sql (SQLite syntax, only types Postgres also has). The mapping from a document is mechanical:

FirestoreSQL
camelCase fieldsnake_case column
booleanINTEGER 0/1 (BOOLEAN in Postgres)
array of skill ids<entity>_skill(<entity>_id, skill_id, pos)
array of strings or objectschild table with pos
l10n overlayl10n(collection, id, lang, field, value), arrays as JSON text
site/shell, live, profile, settingssite_doc(id, data) as JSON; never joined
"Used at ..." (derived in code)the view skill_usage

What changes: the rules disappear, so only a server may read the tables and it always filters visible = 1. The browser cannot hold database credentials, so every run-time read needs a small read API (for example a Worker with D1). Only site/shell is read at build. The app code is unchanged because it depends on ContentRepository, not on Firestore.

This path was proven on the real data before the design folder was retired: every document loaded into SQLite and read back identically, and the SQL view for skill usage gave the same result as the code.

9. Reads and caching

Each document returned is one billed read (free tier: 50,000 reads a day). Measured on the live site, one parallel batch per page:

PageFirestore callsAbout
Homesite/live, site/profile, contacts, skills, experience, projects86 reads
Resume+ educationabout 80-90 reads
Projectslive, profile, contacts, skills, projectsabout 80 reads
QuerystaleTimeOther
site/live60 srefetch when the tab regains focus
profile, settings, collections5 minutespersisted to localStorage for 24 h; bump the cache version when the schema changes

Returning visitors read from the persisted cache and only refetch what is stale. Idea for later: load blocks below the fold when they near the viewport, load the Connect menu on open, and read only listed skills on Home.

10. Operations

TaskHow
Back up the datanpm run backup:firestore writes backup/firestore-v2.json (every v2 collection, hidden items included) and backup/messages.json. The folder is git-ignored: it holds payment details and visitors' emails.
Restorenpm run restore:firestore -- backup/firestore-v2.json prints a plan; add --apply to write. It overwrites the backed-up documents and deletes extra ones in v2 collections; v1 and messages are never touched.
Deploy rulesnpx firebase-tools deploy --only firestore:rules (changes production; back up first).
Refresh the test snapshotcopy a backup to tests/fixtures/seed.json and replace real payment accounts with fake ones (the repository is public).
