bach-cv: detail design

How the site is built: context, architecture, the main flows, states, shared blocks, errors, security, delivery and tests.

1. System context

A static site on Firebase Hosting. All dynamic data comes straight from Firestore in the visitor's browser; the only other server-side piece is the chat Worker.

PartRoleNotes
Firebase Hostingserves out/HTML revalidates every load; /_next/static is cached for a year, /fonts for 30 days; HSTS, Content-Security-Policy, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy.
Firestorecontent, switches, contact messagesfree tier; protected by rules, not by hiding the URL; App Check tokens are sent but not yet enforced
Cloudflare Workerchat proxy and email notification/chat: validates, rate-limits per visitor (KV), tries Workers AI then Gemini, caps the answer at 1024 tokens. /notify: emails the owner about a saved message. Keys live in the Worker.
Workers AIanswers the chatfree daily allowance of the Cloudflare account, no API key; a spent allowance falls back to Gemini

Dependencies flow downward. Components never import Firebase; only the Firestore adapter does, and only the lite SDK.

3. Pages and routes

Every page is a static file. A page that is not Home is wrapped in <PageShell page="...">, which sets the page colours, renders the header and footer and applies the page switch. Home uses the same gate inside its own layout.

Header and menus read site/live and contacts on every page. The chat widget and the language switch are mounted for the whole site.

Each page has its own title, description, canonical link and social preview in its static HTML (English, for search engines and link previews). DocumentTitle then sets the tab title in the visitor's language and keeps it when the framework resets it. The root layout also carries a schema.org Person. public/sitemap.xml lists the six public pages; /payment is left out and disallowed in robots.txt.

4.6 Switching language

The visitor picks EN or VI. LanguageProvider updates its state, stores the choice in localStorage (bach-cv-lang) and sets <html lang>. Components read copy with useCopy; useContentQuery re-lays l10n over the cached documents. No refetch happens. The first paint is always the default language, so the static HTML and the first client render agree; the saved or browser language applies right after.

5.3 Blocks that read data

Every block that reads a collection goes through one component, DataState, so loading, empty and failed look the same on every page. The words are in src/content/copy/states.ts (English and Vietnamese).

5.4 Colour theme

The visitor chooses System, Light or Dark in the header (or the phone menu). System follows the operating system and changes with it. A choice is kept in localStorage (bach-cv-theme; System removes the key).

PartHow it works
Before the first painta small inline script in <head> reads the choice and the system setting and puts the dark class on <html>, so a dark visitor never sees a white flash. The CSP already allows inline scripts.
After hydrationThemeProvider reads the saved choice (the first render says System, so the static HTML and the client agree), keeps the class in step and listens for the system setting changing.
Colourstokens in globals.css: :root for light and .dark for dark (background, text, card, border, the category tag pairs, the error colours, the dark panels). Components use tokens, not hex values.
Page colourseach page has one accent and one tint (light values, set per page). In dark the accent is lightened and the tint is a wash of the accent over the page background, derived in CSS, so no page needs a second pair of colours.
Stays lightthe CV sheets (preview and skeleton) carry theme-light, which restores the light tokens inside them. The PDF is not themed. QR codes and screenshots keep their white background.
Checksa unit test measures the contrast of every token pair and every page colour in both themes; a browser test fails on text that is hard to read on its background in dark mode, and checks the menu, the saved choice, the system setting and the CV sheet.

5.5 Skins

A skin is another look for the same content. The visitor picks Standard or Dev (the site as the window of a code editor) in the header; the choice is kept in localStorage (bach-cv-skin, or ?skin=dev) and the URL does not change. The static HTML is always Standard.

PartHow it works
Before the first painta small inline script in <head> puts the saved choice on <html data-skin>; the body stays hidden until data-skin-ready. Standard visitors get no attribute and no delay. If the skin has not become ready after 8 seconds, the script removes the attribute and Standard shows (no blank page when a chunk fails to load).
LoadingSkinFrame shows Standard (children) or loads the skin with import() from the registry. A skin is a SkinDefinition: Frame, one component per page, NotFound, Maintenance; a missing page does not compile. Its code is downloaded only when chosen.
Same contenta skin reads the same hooks (lib/query, use-live) and the same interface copy as Standard, so data states, errors, switches, keyboard and both languages behave the same. Layers do not change: a skin sits beside components and never imports Firebase.
Stylingone Tailwind build for every skin (globals.css scans src/skins); the Dev palette is theme colours whose values sit on html[data-skin='dev'], dark and light, and the shadcn tokens are mapped to it so dialogs follow the skin. CSS files hold only keyframes, view transitions and token colours.
Dev only: Terminala small working shell in the bottom panel (help, ls, cd, cv, connect, ask, clear, exit) that drives what Standard already has: navigation, the CV window, the Connect menu and BB Bot. It honours the site/live switches (a hidden page does not exist, a soon page says so).
Dev only: Output and Problemsa log of the current page load in the format of logcat, built only from typed events and allow-lists (route, collection names, counts, durations, language, theme, skin, which window opened). It never holds document contents, emails, URLs, messages or raw error text, lives in memory, is never sent and never printed to the console. Problems lists the failed queries and runtime errors.
Dev only: Connectthe account menu is a command palette at the bottom left (a bottom sheet on a phone): type to filter, arrow keys, Enter; same links, email with Copy, and location as Standard.
Dev only: window lightsthe three lights of the title bar work: red closes the editor (back to the Standard look, the same as the Skin menu), yellow is Zen mode (the chrome around the page is hidden with CSS, so nothing is unmounted and the terminal keeps its scrollback; Esc or the light leaves it, an open window takes Esc first), green is the full screen of the page (the Fullscreen API; grey where the browser cannot do it). A phone has no lights.
Dev only: motiona page change is a view transition (<ViewTransition key={page}> in the shell): the window stays, the page fades out and the next fades in, and the green line of the open tab glides to its new tab (the one element named dv-tabline). The sync icon of the status bar turns while TanStack Query is fetching, the problem count nudges when it goes up, and the bottom panel rises when it opens. The photos of About zoom slowly and their frame takes the accent colour. All off for reduced motion.
Browser storagebach-cv-skin for the choice and bach-cv-dev-ui for the chrome of the Dev skin (Explorer, folders, panel: booleans and paths, no personal data).
CSPthe policy of firebase.json applies to every skin. The Dev picture viewer asks the image host for the size and for Download; both are refused on the live policy and the viewer degrades on purpose (no size, Download opens the picture in a new tab).
Checksunit tests for the skin ids, the CSS rules, the terminal and the log (hostile values fed to every event); a Playwright spec per area runs the same visible checks in the Dev skin (shell, home and about, resume and certificates, projects and payment, services, overlays, terminal, output, hover, motion) and one switches skins.

7. Errors and fail-open behaviour

SituationWhat the visitor sees
site/live cannot be readdefaults: every page and feature on, no maintenance
a collection query failsthat block shows its error or empty state with Try again; the rest of the page works
one malformed documentit is skipped (parsed with safeParse); the others show
no translation for a fieldthe English text
Firestore quota exhaustedblocks stay empty; the static shell, name and photo remain
chat proxy empty or downthe panel says the assistant is not available; the input is disabled
Workers AI allowance spent or an errorthe Worker tries the next provider (Gemini); the visitor sees the answer
every provider failsthe chat error note (rate limit, or a general error) with Try again
an old Worker that still requires a providerthe app asks once more with provider: "gemini", so the site and the Worker can be deployed in any order
the email notification fails or is not configurednothing: the message is already saved, and the visitor sees Message sent
App Check token cannot be obtainedthe request goes without a token; it only matters once enforcement is on
chat rate limit / daily limit / networka specific note and Try again; the conversation is kept
message send failsthe text is kept and Try again is offered
PDF fails to buildthe dialog stays open; the preview still works

8. Security

TopicDecision
Data exposurethe rules return only visible == true documents; payments are read only on the Payment page and are never embedded or sent to the chat model
Writesthe browser can only create a validated messages document; the old v1 collections (config, user, message) are closed (their data is kept in a backup)
Secretsno secret in NEXT_PUBLIC_*; model keys live in the Worker; service account files are git-ignored
Public repositoryno real account numbers in fixtures; backup/ is ignored
HeadersHSTS, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy and a Content-Security-Policy: scripts from the site and reCAPTCHA (plus WebAssembly for the PDF), connections to the site, Firestore, the Worker and App Check, https images, no frames except reCAPTCHA, no eval. It was checked against every page, the dialogs, the CV preview, the PDF download and the chat.
App Checktokens are sent with Firestore requests (reCAPTCHA Enterprise). Enforcement is off: when on, Firestore refuses every request without a token, reads included, so a visitor whose browser blocks reCAPTCHA would see no content. Watch the metrics first.
Workeronly the providers in ALLOWED_PROVIDERS are served (a caller cannot spend OpenAI or Anthropic credit); answers capped at 1024 tokens; a visitor limit per minute and per day in KV, required (REQUIRE_RATE_LIMIT); the model key goes in a header, not in the URL; CORS names only this site; secrets are Wrangler secrets
Email notificationthe Worker sends nothing without the KV limit; at most 5 per visitor per hour and 40 per day for the whole site (the free email plan allows 100 a day); one email per address; a line break in the name cannot add a header
Abusehoneypot on the form; Worker limits; Firestore rules cap sizes. Nothing stops a script from writing straight to messages within those rules; App Check enforcement would.
Maintenance and page switches are UI only. Do not use them to protect data; use visible.

11. Decisions and known limits

Decisions

  • Static export on free hosting, data read in the browser, only the shell embedded.
  • Firestore lite, not the full SDK: no listeners needed, smaller bundle.
  • Interface copy in code, content in Firestore, translations as an overlay.
  • Per-document visible enforced by rules instead of filtering in the client.
  • A repository interface so the database can change.
  • The chat does not name a provider: the Worker owns the order and the fallback, so a model can change without a site release.
  • The email is a nudge after the save, never part of it.
  • One data-state component and one action vocabulary, so pages cannot drift apart.
  • The theme is a class on the root and tokens, not a second stylesheet: a new colour has two values in one place.
  • A skin changes presentation, never content or features; the Terminal, Output and Problems tabs of the Dev skin only drive or report what Standard already has.
  • One Tailwind build for all skins: a second stylesheet loaded later reorders utilities of the same name and breaks the Standard header.

Known limits

  • The static HTML (search results, link previews) carries English titles and descriptions; only the tab title follows the language.
  • The illustrations on the Services page keep their own colours in dark mode (they are drawings of an app window); they sit on a tinted tile.
  • The CV and PDF omit hidden roles (TMA, EasyGDS, Freelancer).
  • Switches fall back to "on" while loading, so a maintenance screen can appear a moment after the content.
  • No Firestore emulator run for the rules; they are checked against the real project.
  • The Gemini key in the Worker is currently invalid, so the chat depends on the Workers AI daily allowance; its small free models answer Vietnamese less well than Gemini.
  • Email reaches only the Resend account's own address until a domain is verified.
  • App Check is not enforced (see Security). Messages can still be written by a script within the rules.
  • Free tiers change often (Workers AI, Resend, reCAPTCHA): check their pages before relying on a limit.
  • Because the Dev skin shares the Tailwind build, the Standard stylesheet is about 35 KB gzip (it was about 20 KB); the scripts of the skin still load only when it is chosen. A lazy, scoped stylesheet would remove the difference.
  • On the live CSP the Dev viewer logs one console violation per picture (the size request to the image host) and has no size in its status line.
  • Skills are read in full (62 documents) even where only the listed ones are shown.
